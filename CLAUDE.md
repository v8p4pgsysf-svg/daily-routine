# Weekly Routine — notes for Claude

Weekly Routine (renamed from Daily Routine on 2 Nov 2026; the repo and URL keep `daily-routine`, since renaming would break installs) is a personal health and fitness tracker (daily check-ins, weekly review, strength and cardio logging, progress charts) used by Jack, and optionally his girlfriend and friends. It runs as a home-screen web app.

## How it fits together
- `src/weekly-routine.html` is the single source of the app. It began as a Claude artifact, so it still talks to storage through a `window.claude.use(...)` interface. That interface is now supplied by `docs/host.js`. The old Claude artifact version is retired (31 Oct 2026), so don't republish it.
- `docs/` is the live app on GitHub Pages: https://v8p4pgsysf-svg.github.io/daily-routine/
  - `docs/host.js` signs people in (email and password, through Supabase Auth). It then supplies the same `db` / `user` / `assets` / `downloads` interface the page expects, backed by Supabase. Finally it runs the page's script, which `tools/build.py` embeds as `<script type="text/plain" id="app-src">`.
  - `docs/config.js` holds the Supabase URL and publishable key. These are public by design.
  - `docs/supabase.js` is a vendored copy of @supabase/supabase-js 2.117.3 (UMD).
- Supabase project `xneuqsjqhlzhpqmcacst` (London) holds all user data.
  - The `public.docs` table has one row per record. It has RLS, and each person sees only their own rows.
  - Photos live in a private `photos` bucket, under `<user id>/<photo id>`, **encrypted on the device** (AES-GCM; files start `RPE1`, labelled image/jpeg so the bucket accepts them). Each person's random photo key is in their `docs` row `data/users/<uid>/private` / `photokey`, locked twice: by their password (PBKDF2, 310k) and by a recovery code (shown once, before their first encrypted photo; Settings → Photo recovery code explains it first, and "Make a new code" replaces it only once they tap "I've saved it"). The unlocked key is cached on the device as `routine-pk` (cleared on sign-out). All in `docs/host.js` (`initKey`, `askUnlock`, `ensureRc`, `put`, `load`, `secureOld`). Flows: sign-in/sign-up pass the typed password to `start()`; a device without the key asks for the password once if they have photos; after a forgot-password reset it asks for the recovery code (or "Start fresh": old photos show locked); changing password re-locks the key; older plain photos are encrypted in place once a recovery code exists; Export gets decrypted photos via `HOST.photoBlob`. I (Claude) can't see the live Supabase; Jack can see files in Storage → photos (unreadable now). Test: `tests/hosted/photo-encryption.py`.
  - `supabase/schema.sql` sets all of this up and is safe to re-run.
- Accounts: people sign up themselves in the app (email + their own password), but only if their email is in `public.invites`. A `before insert` trigger on `auth.users` enforces this, so it can't be bypassed (`supabase/invites.sql`). An invite code also works: it's kept in `public.app_config` (`invite_code`), the app sends it as sign-up metadata, and the same trigger checks it (`supabase/accounts.sql`, which also adds `delete_my_account()`). Email confirmation is off. **Forgot password?** (sign-in card) emails a 6-digit code via `signInWithOtp` (`shouldCreateUser:false`), then `verifyOtp` (type `email`) + `updateUser` set the new password on the same card, so it all stays in the Home Screen app (a reset *link* would open Safari). The code comes from Supabase's **Magic Link** email template (`{{ .Token }}`), sent through custom SMTP (a dedicated Gmail account with an app password). Test: `tests/hosted/forgot-password.py` (the mock's code is always 123456). The page hides hosted-only UI (import, account section) unless `window.__routineHost` exists.
- Home Screen nudge (`addInstallHint` in `docs/host.js`): on a phone browser that isn't the Home Screen app, the sign-in page leads with "Add to your Home Screen" and the steps, and the form waits behind "Continue in … instead" (remembered as `routine-a2hs-skip`). Same heading on every phone; only the steps differ. iPhone: Share steps, worded for any iOS version. Android: the ⋮ menu steps, swapped for a real Install button when the browser offers one. In-app browsers like Instagram: "Open in Safari/Chrome first". Desktop: nothing. Test: `tests/hosted/home-screen.py`.
- Feedback: a speech-bubble icon left of the cog (hidden below 375px wide; the tabs' padding was trimmed to 12px so it fits) and **Settings → Send feedback** for everyone open the same sheet (`openFeedback`). It sends through `HOST.sendFeedback` to `public.feedback` (`supabase/feedback.sql`): people can insert as themselves but not read; the database fills in their email; app version (a `meta[name=app-version]` stamped by `tools/build.py`) and device go with it. Jack reads it in Table Editor → feedback. Test: `tests/hosted/feedback.py`.

- Settings: `normaliseSettings` validates every key it reads and keeps any key it doesn't know (`SETTINGS_KNOWN` lists the ones it reads), so older copies of the app don't drop settings added later. When adding a setting, add its key to `SETTINGS_KNOWN` and validate it there.

## Single sources: add things in one place
Each of these lives in one list in `src/weekly-routine.html`; everything else is derived from it. Never change an existing id or key once people have used it.
- `HABIT_CATALOG`: daily habits (protein, fruit & veg, sleep, steps, no alcohol, no nicotine). People can add up to 8 of their own (`settings.custom`, keys `x_…`): one line to add, counted daily out of 7 like protein, with an optional target. These feed setup, settings, the check-ins grid, counts, the review summary and exports.
- `EXERCISE_CATALOG`: exercises, each with a name, a short name for the key-lifts table, its weight step, and whether it's assisted. These feed the exercise picker, programmes, workouts, the progress dropdown, key lifts, lift status and exports. People's own exercises are stored in `settings.exNames`.
- `PRESETS`: suggested programmes, each with its own workouts and suggested days (both Mon, Wed, Fri, which is also where setup starts). Since 2 Nov 2026 the "3-day full body" preset no longer equals `DEFAULT_SETTINGS.workouts` (Jack's original routine, kept for the retired Claude version and the tests). People keep the copy they chose; an updated preset reaches them only if they Switch to it in Settings.
- `CARDIO_CATALOG`: cardio types offered as chips. Everything logged counts toward the weekly target; the old Walk chip is gone, and walks dated before `WALKS_COUNT_FROM` (2 Nov 2026) keep not counting so past weeks don't change.
- `PREP_INFO`: prep tasks. These feed setup, settings, Today, the planned week and the grid.
- `DAYS` / `DAYS_LONG` and `LETTERS` hold day names and workout letters.

## Habits, setup and settings
- Weights are stored in kg. `settings.unit` (kg/lb) only changes display and input; use `liftU`/`fromU`/`fmtLift`/`fmtBody`. Exports stay in kg.
- Setup opens on a **Welcome page** (step 1 of `SETUP_STEPS`): the app's story as three points from `WELCOME_POINTS` ("Plan your week", "Train and tick off habits", "Review how it went"), all closed, each opening to say what it means in the app. The button at the bottom (pinned, `.swfoot`, so it doesn't move as points open; only one point is open at a time, by Next or by tapping) says Next and opens each point in turn (`welNext`); once all three have been opened (by Next or by hand) it becomes Get started (`welBtn`). No Next in the top bar and no dots on that page; the dots count the five steps after it. The sign-in card carries the same story as one line under "Weekly Routine".
- Setup then asks for a weight first. It's saved as that week's weigh-in and sets the protein target (1.6 g per kg, rounded to 5 g).
- The settings page and the first-time setup share pieces: `habitRows`, `secCounts`, `secGrid`, `secLists`, `secPrep` and `secPresets`.
- Setup runs once, in the hosted app only. It starts after cloud data has loaded, and only when the person has no saved settings, no data and no `setupDone` marker. Finishing setup saves `setupDone: true` with their settings.
  - New people start from neutral defaults (`newcomerDraft`). Jack's routine stays the default only for the Claude version.
- **Starter week**: setup saves `settings.startedOn` (the day they finished it, never changed). The week containing it counts only from that day: `habitsFor` runs `fitStarter`, which fits each target to the days left (daily habits out of the days left, "6+ days" targets scaled, strength/cardio/prep = planned days left; a row with nothing left is `off`: shown as "From Monday", not counted). Days before the start are dots. Header says "% of check-ins" like any week, Today has a Starter week line, the review is "Starter review" with starter questions, and the chart shades that week and leaves it out of the average. No `startedOn` (Jack, older data, a restored backup) or a Monday start = an ordinary week. When past weeks are stamped (any settings change), a starter week stores its fitted targets (`plan.fitted`), so later settings changes don't rewrite it. Someone who joined mid-week sees the Starter week line instead of the first-day tip.
- **Early days (empty charts)**: on Progress, `foldProgress` (run after `renderCharts` and `renderStrengthTrends`) hides each chart whose content is an `.empty` box and puts one note per section (`#trends-note`, `#training-note`) naming what's still to come; a chart returns to its place as soon as it has data. On Training, history shows one note until something is logged, and Exercise progress is hidden until then (one line, no exercise menu, until a lift has data).
- The late-review nudge shows the day after review day only (Monday for a Sunday review); after that the review is missed for its week but can still be completed there.
- Weights per week can be 0. In that case there's no Strength row, and Training offers cardio only.
- History and the workout screen show a swapped or added exercise's note on its own line (`exNote`: "Instead of …" / "Added"). The workout screen also says "Last time you also did Set N: …" when last time had more sets than today's rows (never carried forward; + Set adds it).
- **Habits only** (`habitsOnly()`: 0 weights and 0 cardio): `renderTabs` hides the Training tab (unless they have logged sessions: `trainingTab()`) and Planned week; Today has no Rest card; setup skips the planned-days step.
- Suggested programmes live in `PRESETS`.

## Making a change
1. Edit `src/weekly-routine.html`.
2. Run the tests: `node tests/app.test.js src/weekly-routine.html`. This needs `npm i jsdom`, and all checks must pass. For sign-in, setup or sync changes, also run the hosted suites: `tests/hosted/setup.sh <folder>`, then `python3 run.py` (and the others) in that folder. All suites run on a fixed calendar, so results don't depend on the real date.
3. Rebuild: `python3 tools/build.py`. This rewrites `docs/index.html` and `docs/sw.js`; the new cache version makes phones pick up the update.
4. Commit and push to `main`, in batches: only when the tests are clean, and not several pushes in a few minutes (GitHub Pages rejects a deploy while it still counts the previous one as in progress). GitHub Pages redeploys in a minute or two. Phones open the saved copy instantly, pick up the new version in the background, and show it on the next open.
5. Check the deploy before saying it's live: `gh run list -R v8p4pgsysf-svg/daily-routine -L 1` should show the Pages run as success for your commit. If it failed with "in progress deployment", wait a few minutes and push an empty commit.
